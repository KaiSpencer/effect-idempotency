# Limits [What the middleware does not do]

## Large and streamed bodies

[Streams and uploads](/behaviour/streams) has the details. In short:

- A response over `maxStoredBytes`, 1 MiB by default, is sent but not stored,
  so a retry runs the handler again.
- A response whose body is a file or form data is sent but not stored either.
- A streamed response is stored once it has ended. Until then a retry is
  answered `409`.
- A request payload that is a stream or a multipart upload is read whole
  before the handler runs, unless the endpoint leaves the body out of the
  fingerprint with `Idempotency.FingerprintBody`.
- A multipart retry whose form was encoded again, with a new boundary, is a
  different request and is answered `422`.

## Checks inside the handler are not repeated

A replay does not run the handler, so a permission check inside the handler is
not repeated. Put checks that must hold on every request in a middleware that
runs outside this one, as authentication does: see
[Scope](/behaviour/scope#run-authentication-first).

## The body is compared byte for byte

The same JSON with different whitespace or key order is a different request,
and is answered `422`. A retry that resends the bytes it sent before is not
affected. An endpoint that leaves the body out of the fingerprint compares its
digest headers instead: see
[Streams and uploads](/behaviour/streams#leaving-the-body-out-of-the-fingerprint).

## One key header per request

Two `Idempotency-Key` headers are refused, because they arrive joined by a
comma and which key was meant cannot be told. See
[The key](/behaviour/key#quoted-and-bare).

## Store limits

Each store has limits of its own:

- [Memory](/stores/memory#limits): one process, lost on restart, no size
  limit.
- [SQL](/stores/sql#limits): PostgreSQL and SQLite only.
